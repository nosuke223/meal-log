# 公開サービスの手引き

誰でも登録できて、お金を取れる Web サービスを作るときに読む手引きです。相談役は Issue を書くときに、実装エージェントは作るときに、この手引きに従います。データをサーバーに保存する部分は [server-storage.md](server-storage.md) にあり、この手引きはその上に重ねます（所有者だけが使うときの Access の代わりに、会員登録とログインを使います）。

部品の選び方と比べた結果は、agent-env の「公開サービスの部品表」（2026-11-10。所有者が決めた）にあります。ここでは、決まった標準の組み合わせと、作りの決まりを書きます。値段や上限は変わるので、使い始めるときに各社の公式の案内で確かめます。

## 標準の組み合わせ

| 部品 | 標準 | メモ |
| --- | --- | --- |
| 公開先・API | Cloudflare（Pages / Workers） | 公開したら Workers の有料プラン（月 $5） |
| データベース | Cloudflare D1 | [server-storage.md](server-storage.md) のとおり |
| ログイン | Better Auth（Workers と D1 の上で動く library） | 会員のデータは自分の D1 に置く |
| 決済 | Stripe | 支払いの画面は Stripe のものを使う |
| メール | Resend | Cloudflare Email Sending が正式版になったら寄せる |
| 不具合と死活の監視 | Sentry と死活の監視 | 届け先は Discord と Issue |
| バックアップ | D1 のさかのぼり ＋ 毎日の書き出し（R2） | |
| ドメイン | Cloudflare で取る | |
| 苦手なものの逃げ道 | Cloudflare Containers | 重い処理や常駐の処理が要るときだけ |

ほかの部品を使いたくなったら、Issue を書く前に、agent-env のセッションで所有者と決め直す（部品を増やすと、手引き、通信の許可、プレビューの読み取りなどが増えるため）。

## 1. 先に決めること（相談役が所有者に聞く）

| 決めること | おすすめ | 理由 |
| --- | --- | --- |
| 料金のプラン | 無料のプランと、有料のプラン1つ（月額）から始める | 最初から段階を増やすと、画面と決まりが増える |
| 有料でできること | 無料のプランの上限（件数など）を外す形 | 無料の人の使い方を壊さずに済む |
| 支払いの方法 | 毎月の自動の課金はカード（Apple Pay、Google Pay を含む）だけ | コンビニ払いや振込は、毎月の自動の課金にできない（請求書を送ってその都度払ってもらう形になる） |
| ログインの方法 | メールアドレスとパスワード（メールの確認とパスワードの再設定つき） | Google などでのログインは、所有者が各社の画面で設定する作業が増えるので後から足す |
| プレビューで登録と支払いを試すか | 試す。プレビュー用の D1 と、Stripe のテストのモードの鍵を使う | 公開サービスでは、所有者がプレビューで登録から支払いまで触って確かめるため。本番のデータと鍵は、プレビューに入れない |
| 規約などのページ | 利用規約、プライバシーポリシー、特定商取引法に基づく表記を用意する | お金を取るサービスで必要。中身の事実（事業者の名前、連絡先、料金、解約の決まりなど）は所有者が出し、文はエージェントが下書きする。所有者が読んでから公開する |

## 2. ログイン（Better Auth）

- Workers と D1 の上で動かす。会員、セッション、メールの確認などの表は、`migrations/` の SQL で作る（D1 のマイグレーションと同じ流れで、本番には所有者がマージの前に当てる）
- 秘密の値 `BETTER_AUTH_SECRET` は、所有者が `wrangler pages secret put`（本番とプレビューで別の値）で入れる。リポジトリには書かない
- セッションは cookie に入れる（`HttpOnly`、`Secure`、`SameSite=Lax`）。画面の JavaScript から読めないようにする
- すべての API の読み書きを、ログインしている会員の ID で絞る（[server-storage.md](server-storage.md) の「データの読み書き」と同じ考え方。メールアドレスの代わりに会員の ID を使う）。他の会員のデータが見えない・変えられないことをテストで確かめる
- ログインとパスワードの再設定には、試す回数の上限を付ける（総当たりを防ぐ）
- パスワードの再設定とメールの確認のメールは、部品 4（Resend）で送る
- 所有者だけが使う管理の画面が要るときは、その画面だけ Cloudflare Access で守る
- Better Auth の D1 への対応や、マイグレーションの作り方は、版によって変わる。作る前に、公式の文書（better-auth.com）の Cloudflare と D1 の説明を読む

## 3. 決済（Stripe）

- 支払いの画面は Stripe Checkout（Stripe が用意する画面）を使う。カードの番号は、自分のサービスを通さない
- プランの変更、支払い方法の変更、解約は、Stripe のカスタマーポータルを使う
- 支払いの結果は、Stripe からの通知（webhook）で受け取り、D1 の会員のプランを更新する
  - 受け口は `/api/stripe/webhook`。署名を必ず確かめる（Workers では、Stripe の library の fetch 用の通信と Web Crypto 用の確かめ方を使う）
  - 同じ通知が2回届いても、二重に処理しない（処理した通知の ID を記録する）
  - 会員のプランの正しい値は Stripe にある。D1 はその写しとして持つ
- 秘密の値 `STRIPE_SECRET_KEY` と `STRIPE_WEBHOOK_SECRET` は、所有者が入れる。プレビューにはテストのモードの値だけ、本番には本番の値を入れる。エージェントは本番の値を見ない
- テスト: 単体のテストでは Stripe を偽物に差し替える。プレビューでは、Stripe のテスト用のカード番号で、登録から支払い、解約まで所有者が試す
- 決済に関わる Issue には `merge:manual` を付ける（取り消しにくい変更のため。所有者がプレビューで支払いを試してからマージする）

## 4. メール（Resend）

- 送信元は、サービスのドメインのアドレス（例: `no-reply@<ドメイン>`）にする。所有者が Resend にドメインを登録し、Resend が示す DNS の設定（SPF、DKIM）を Cloudflare の DNS に入れる
- 秘密の値 `RESEND_API_KEY` は、所有者が入れる
- メールの文面はリポジトリのファイルに置き、エージェントが直せるようにする
- プレビューから実在のアドレスにメールを送らないよう、プレビューでは送り先を所有者のアドレスだけに限るか、送らずに記録だけにする

## 5. 不具合と死活の監視

- Sentry の SDK を、画面（ブラウザ）と API（Workers）の両方に入れる。エラーが起きたら Sentry に集まる。利用者のメールアドレスなどの個人の情報は送らない
- 状態を確かめる受け口 `/api/health` を作る（D1 に読みに行けるかも確かめる）。死活の監視が数分ごとに開き、止まっていたら知らせる
- 知らせる先: 所有者が Sentry の画面で、Discord への通知を設定する（要対応のチャンネル）
- エラーを Issue にして、リードが仕分け、エージェントが直す流れは、agent-env の側で作る（Sentry からの読み方は、そのときに決める）
- 費用: Sentry の無料のプランは、月 5,000 件のエラーまで（1人）

## 6. バックアップ

- 1段目: D1 のさかのぼり（Time Travel）。有料のプランで30日（無料は7日）。誤って消したときに、時刻を指定して戻す
- 2段目: 毎日1回、Cron Trigger で動く処理が、会員と記録の表を JSON にして R2（Cloudflare のファイル置き場）に保存する。30日より古いものは消す
  - 書き出したものから戻せることを、テストで確かめる（戻す処理も用意する）
  - 書き出しには個人の情報が入るので、R2 の置き場は公開しない
- 戻すのは、所有者の承認を通してから行う（エージェントが本番のデータを書き換えない）

## 7. ドメイン

- 所有者が Cloudflare でドメインを取り、Pages のプロジェクトに独自のドメインとしてつなぐ
- 画面とメールの送信元を、同じドメインにそろえる

## 8. 所有者の作業の一覧（一度だけ）

Issue の「所有者にしてほしいこと」に、いつするか（着手の前／マージの後）と一緒に書く。

| 作業 | いつ |
| --- | --- |
| Stripe のアカウントを作り、事業者の情報を登録する。テストのモードの鍵をプレビューに入れる | 決済の Issue の着手の前 |
| 本番の鍵（Stripe、Better Auth の秘密の値）を本番に入れる | 公開の直前 |
| Resend のアカウントを作り、ドメインの DNS を設定する。鍵を入れる | メールの Issue のマージの後（ドメインを取った後） |
| Sentry のプロジェクトを作り、DSN（秘密ではない）を伝える。Discord への通知を設定する | 監視の Issue の着手の前 |
| ドメインを取り、Pages につなぐ | 公開の前 |
| Workers の有料プラン（月 $5）にする | 公開の前 |
| プレビュー用の D1 を作り、Pages の「Preview」につなぐ | ログインの Issue の着手の前 |
| 規約などのページの事実（事業者の名前、連絡先、料金、解約の決まり）を出し、下書きを読む | 規約のページの Issue の着手の前とマージの前 |

## 9. Issue の分け方（おすすめの順番）

1. ログイン（会員登録、メールの確認、パスワードの再設定）。メールの送信もここで作る
2. データを会員ごとに分ける（所有者だけのときの Access から切り替える）
3. 監視（Sentry、`/api/health`）
4. バックアップ（毎日の書き出しと、戻す処理）
5. 料金のプランと決済（テストのモード）。`merge:manual`
6. 規約などのページ。`merge:manual`
7. 公開（ドメイン、本番の鍵、有料プラン）。所有者の作業が中心

順番のある Issue には「着手の条件」を書く。1 と 2 は同じ部分を変えるので、2 は 1 の後にする。
