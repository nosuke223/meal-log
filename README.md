# meal-log

その日食べたものを記録し、カレンダーから過去の分も確認できる食事記録の Web アプリです。食べる予定のものも入力できます。

現在は、1日分の食事を記録する画面と、過去の記録を見返すカレンダーと、記録をファイルに書き出し・読み込みするデータ画面があります。食べる予定のものも、先に入力できます。

画面はスマホの縦画面を優先しています。アプリを開くと、今日の記録の画面が表示されます。

記録はサーバー（Cloudflare Pages Functions と D1）に、ログインした会員ごとに保存します。記録の画面、カレンダー、データ画面は、会員登録してログインすると使えます。別のブラウザや別の端末でログインしても、同じ会員なら同じ記録が見えます。他の会員の記録は見えず、変えられません（ブラウザ内には記録を残しません）。通信が切れているときは使えません。

Cloudflare への公開と Access（公開の準備までの間、サイト全体を所有者だけが開けるようにする設定）の手順は、[docs/deploy.md](docs/deploy.md) にあります。

## 記録の画面でできること

表示している日の日付と、朝・昼・夜・間食の4つの欄が表示されます（記録がなくても欄は表示されます）。最初は端末の現地の今日の画面で、カレンダーから選んだ過去の日や明日以降の日の画面でも、同じ操作ができます。

- 品の追加: 欄ごとに品名を入力して「追加」を押す。欄の中は作成した順に並ぶ。品名が空（空白だけ）のときは押せない
  - 今日と明日以降の日に追加した品は「予定」、過去の日に追加した品は「食べた」で保存される（下の「予定と食べた」）
- ジャンル（和・洋・中・その他）と料理の分類（主食・主菜・副菜・汁物・その他）: ボタンで選ぶ。選んだボタンをもう一度押すと未設定に戻る
  - 追加するとき、ジャンルは同じ区分の直前の品のものが最初から選ばれる（押して外せる）。料理の分類は引き継がない
- 品の変更・削除: 追加済みの品をタップすると、品名、ジャンル、料理の分類、区分、日付を変更できる。区分を変えると変更先の欄に、日付を変えるとその日に移る。「削除」は確認の後に行う
- エラー: 通信の失敗やサーバーのエラーなどで、読み込みや保存に失敗したときは画面にエラーを表示する。保存されている記録は消えない（入力中の品名も残る）
  - 保存（追加、変更、削除、予定と食べたの切り替え）はできたが、その後の一覧の読み直しだけに失敗したときは「保存しました。一覧を読み込めませんでした: …」と表示する。保存できたときと同じく、入力欄は空になり、変更の欄は閉じる。一覧は前の表示のままで、次に読み直しに成功すると（次の保存や、画面を開き直したときなど）、エラーが消えて最新になる
  - 使っている途中でログインの期限が切れたとき（API が 401 を返した。ログアウトした、ほかの端末でパスワードを再設定したなども含む）は、ログインの画面（`#/login/session-expired`）に移り、「ログインの期限が切れました。ログインし直してください」と出す
- 保存先は、サーバー（下の「サーバーの API」）。画面の部品は「保存の窓口」だけを使う
- 最新の記録の読み直し: 開いたままのタブや画面に戻ってきたときに、記録の画面とカレンダーは、保存されている記録を読み直す（別の端末やタブで追加・変更・削除した品が、ページを読み込み直さずに表示される）。一定の時間ごとには読み直さない
  - 入力中の品名と、選んだジャンル・料理の分類は残る
  - 読み直しに失敗したとき（通信が切れている、ログインの期限が切れているなど）は、「記録を読み込めませんでした: …」のエラーを表示し、一覧（カレンダーでは点・予定の印・選んだ日の一覧）は前の表示のままにする。変更の欄を開いている品も消えないので、変更の欄と入力中の内容も残る。次に読み直しに成功すると、エラーが消えて最新になる。日や月を移った最初の読み込みに失敗したときは、前の日・前の月の記録を出さないよう、空にしてエラーを表示する
  - 変更の欄を開いている品が、別の端末で削除されていたときは、その品は一覧から消え、変更の欄も閉じる（入力していた変更は捨てる）
- ジャンルの札: 品に付くジャンルの札（和・洋・中・その他）は、カレンダーの点と同じ色（和=赤、洋=青、中=黄土、その他=緑）で表示する。札には文字も書くので、色だけに頼らず見分けられる。料理の分類の札は、色を付けない灰色の札にして、ジャンルの札と見分ける
- 画面の色: すべての画面（記録の画面、カレンダー、データ画面、ログイン、会員登録、アカウントの画面）は、端末のライトモード・ダークモードの設定にかかわらず、黒に近い背景に白に近い文字で表示する。文字と背景の明るさの差は 4.5:1 以上にしている
- 「カレンダー」ボタン: 表示している日の月のカレンダーを、その日を選んだ状態で開く
- 「データ」ボタン: データ画面（書き出し・読み込み）を開く
- 「アカウント」ボタン: アカウントの画面を開く（下の「会員登録とログイン」）

## 会員登録とログイン

メールアドレスとパスワードで、会員登録とログイン・ログアウトができます。記録は、ログインした会員ごとに分けて保存します。

- ログインしていないと開けない画面: 記録の画面、カレンダー、データ画面。開くと、ログインしているかを確かめ、ログインしていなければログインの画面（`#/login`）に移る（履歴は増やさない）。ログインの画面、会員登録、「パスワードを忘れた」、再設定、アカウントの画面は、ログインしていなくても開ける
- アカウントの画面（記録の画面の「アカウント」ボタン）: ログイン中のメールアドレスと「ログアウト」を出す。ログインしていなければ、ログインの画面を出す
- ログインの画面: メールアドレスとパスワードを入れて「ログイン」。ログインしたら、今日の記録の画面に移る（ログインの画面に移る前に開いていた画面には戻らない）。「会員登録へ」で会員登録の画面に移る。「パスワードを忘れた」で再設定のメールを送る画面（`#/forgot`）に移る
- ログアウトしたとき、別の会員でログインしたときは、前の会員の記録を画面に残さない（記録の画面、カレンダー、データ画面は、初めから読み込む）
- 会員登録の画面: メールアドレスとパスワード（8文字以上）を入れて「登録する」。登録すると「確認のメールを送りました。メールのリンクを開いてください」と出る（ログインした状態にはならない）
- メールアドレスは大文字と小文字を区別しない（小文字にそろえて保存する）
- 入力のエラー（パスワードが短い、メールアドレスの形が違う、パスワードが違う、試す回数の上限を超えた）は、フォームの上に日本語で出す
- 画面からログインの API を呼ぶ部分は `src/auth/`（窓口 `AuthClient`）にまとめている。画面のテストでは、メモリーの中だけで動く窓口（`src/auth/memoryAuthClient.ts`）に差し替える

### 登録とログインの流れ（メールアドレスの確認）

会員登録したメールアドレスが本人のものであることを、メールで確かめます。確認が済むまで、ログインできません。

1. 会員登録の画面で登録すると、確認のメール（件名「【meal-log】メールアドレスの確認」）が届く
2. メールのリンクを開くと、確認でき、ログインの画面（`#/login/verified`）に移って「メールアドレスを確認できました。ログインしてください」と出る。リンクを開いた端末では、ログインした状態にならない
3. ログインの画面でログインする

- リンクの有効期限は24時間。リンクは1回だけ使える（同じリンクをもう一度開くと「すでに使われています」と出る）
- 期限切れ、使用済み、正しくないリンクを開いたときは、ログインの画面にその旨を出し、メールアドレスを入れて「確認のメールをもう一度送る」で送り直せる
- 確認前にログインしようとすると「メールアドレスの確認が済んでいません」と出て、「確認のメールをもう一度送る」ボタンが出る
- すでに登録されているメールアドレスで登録しようとしても、登録できたときと同じ表示になる（登録の有無を外から探られないようにする）。そのアドレスには「すでに登録されています。ログインするか、パスワードを再設定してください」というメールが届く
- メールを送る回数には上限がある（同じメールアドレスと同じ接続元から、10分に3回まで）。超えると「メールを送る回数の上限を超えました。…」と出る

### パスワードの再設定の流れ

パスワードを忘れたときは、メールのリンクから、新しいパスワードを決められます。

1. ログインの画面の「パスワードを忘れた」を押すと、再設定のメールを送る画面（`#/forgot`）に移る。メールアドレスを入れて「再設定のメールを送る」を押す
2. 登録されているかにかかわらず、同じ表示が出る: 「登録されているメールアドレスなら、再設定のメールを送りました。メールのリンクを開いてください」。登録されていないメールアドレスには、メールを送らない（エラーにもしない。応答の内容で登録の有無を探られないようにする）。メールアドレスの確認が済んでいない会員にも送る
3. 届いたメール（件名「【meal-log】パスワードの再設定」）のリンク（`https://<アドレス>/#/reset/<トークン>`）を開く。画面はトークンを画面の中（メモリー）に持ち、アドレスを `#/reset` に置き換える（履歴は増やさない。トークンをアドレスに残さない）。読み込み直してトークンがなくなったときは、「リンクをもう一度開いてください」と出る
4. 新しいパスワード（8文字以上）を入れて「パスワードを変更する」を押す。変更できたら、ログインの画面（`#/login/password-reset`）に移って「パスワードを変更しました。ログインしてください」と出る。リンクを開いた端末でも、ログインした状態にならない

- リンクの有効期限は1時間。リンクは1回だけ使える。期限切れ、使用済み、正しくないリンクは区別せず、「このリンクは、期限が切れているか、すでに使われています。もう一度、再設定のメールを送ってください」と出して、再設定のメールを送る画面（`#/forgot`）へのボタンを出す
- パスワードを再設定すると、その会員のすべてのセッション（ほかの端末のログイン）が切れる
- 再設定しても、メールアドレスの確認が済んだことにはならない（確認が済んでいない会員は、ログインのときに今までどおり確認を求められる）
- 再設定のメールを送る回数と、新しいパスワードを送る回数には上限がある（下の「ログインの API」）
- メールを送れなかったとき（Resend の失敗など）も、登録の有無が分からないよう、応答は変えない。記録（サーバーのログ）に「パスワード再設定のメールを送れなかった」と、エラーの種類だけを残す（宛先とトークンは出さない）

## 予定と食べた

品には「予定」と「食べた」の状態があります。日付（端末の現地の日付）で、次のように決まります。

| 品の日付 | 状態 | 追加したとき | 切り替え |
| --- | --- | --- | --- |
| 明日以降 | 必ず「予定」 | 予定 | できない |
| 今日 | どちらにもできる | 予定 | 「食べたにする」「予定に戻す」のボタンを1回押す |
| 過去 | 必ず「食べた」 | 食べた | できない |

- 品の札で区別できる。予定は紫の「○ 予定」の札と点線の枠、食べたは緑の「✓ 食べた」の札（色だけでなく、文字と形でも区別できる）
- 品の日付を変えたときは、変えた先の日付で決まる。未来の日に動かすと「予定」、過去の日に動かすと「食べた」、今日に動かすとそのときの状態のまま（予定の延期や、記録の日付の間違いを直すのに使う）
- 日が過ぎた予定: アプリを開いたとき、開いたまま日付をまたいだとき、タブや画面に戻ってきたときに、保存されている過去の日の「予定」を、すべて「食べた」にして保存する（更新日時も変わる）
  - 食べなかった品は、削除するか、日付を変えて延期する

## カレンダーでできること

- 月表示（日曜始まり）。「前の月」「次の月」で月を移り、「今月」（ヘッダーの右）で今日の月に戻る。今日のマスは明るい青の枠と暗い青の背景で強調する
- 記録がある日のマスに、その日に出てきたジャンルごとに点を1つずつ表示する（同じジャンルが何品あっても1つ）。「最近中華ばかり」のような偏りに気づくためのもの
  - 点は色（和=赤、洋=青、中=黄土、他=緑）に加えて、文字（和・洋・中・他・未）でも見分けられる。ジャンルが未設定の品の点（未）は、色を付けない点線の枠にする。画面の下に凡例がある
  - 数えるのは「食べた」の記録だけ。予定の記録は数えない
- 予定がある日のマス（今日を含む）には、日の数字の横に、ジャンルの点とは形の違う中抜きのひし形の印を付ける（凡例の「予定あり」）。予定のジャンルは表示しない
  - 日が過ぎて予定が「食べた」になった日は、予定の印が消え、ジャンルの点が表示される
- 日のマスをタップすると、その日を選び、カレンダーの下（凡例の上）に、その日の品の一覧を表示する（画面は移らない）。過去の日、今日、明日以降の日のどれも選べる
  - 選んだ日のマスは、明るい橙の内側の枠（今日以外は暗い橙の背景も）で示す
  - 一覧の見出しは選んだ日の日付。品を区分（朝・昼・夜・間食）ごとに、記録の画面と同じ並びで、状態の札、品名、ジャンル、料理の分類（未設定は出さない）を表示する。品がない区分は出さず、品が1つもない日は「記録はありません」と表示する
  - 一覧には予定の品も出る（ジャンルの点は「食べた」だけを数える）。日が過ぎて予定が「食べた」になると、一覧の札も「食べた」になる
  - 一覧は見るだけ。品の追加・変更・削除、状態の切り替えは記録の画面で行う
  - 今月を開くと今日を選び、ほかの月を開くと何も選ばない（一覧の場所に「日付を選ぶと、その日の品が表示されます」と表示する）
  - 記録を読み込めなかったときは、エラーを表示し、一覧には品を出さない
- 一覧の「この日の記録を開く」ボタンか、選んでいる日のマスをもう一度タップすると、その日の記録の画面が開き、品の追加・変更・削除ができる（明日以降の日では、予定を入力できる）。カレンダーに戻ると点と印と一覧は最新になっている
  - 今日を開くときは、「今日」ボタンと同じ今日の記録の画面を開く
- 「今日」ボタン（ヘッダーの右）: 今日の記録の画面を開く。この画面は、開いたまま日付をまたぐと翌日の画面に変わる（カレンダーから開いた今日以外の日の画面は、その日のまま。ただし、明日以降の日の画面を開いたまま日付をまたいで、その日が今日になったときは、今日の記録の画面に変わり、以後は日付をまたぐと翌日の画面に変わる）

## データ画面でできること

記録をファイルに書き出して保管し、そのファイルから読み込めます。バックアップや端末の移行に使います。記録の画面の「データ」ボタンで開き、「記録の画面へ」で今日の記録の画面に戻ります。

- 書き出し: 「書き出す」を押すと、すべての記録を `meal-log-YYYY-MM-DD.json`（端末の現地の日付）としてダウンロードする。記録が0件でも書き出せる
- 読み込み: 「読み込む」で書き出したファイルを選ぶと、今あるデータと混ぜて取り込む（今あるデータを消して置き換えるモードはない）
  1. ファイルの全件を検査する。不正なら何も取り込まず、理由（何件目が、なぜ不正か）をエラーに表示する
     - JSON として読めない、`version` が対応していない、`records` がない
     - 記録が1件でも不正（検査の規則は、保存の窓口の入力の検査と同じ。下の「記録の形」。加えて `id` が空でない文字列で、`createdAt` と `updatedAt` が窓口の付ける形の日時（例: `2026-11-06T00:00:00.000Z`））
     - 同じファイルの中に同じ `id` が2つある
  2. 追加する件数・更新する件数・変更なしの件数を表示する。「取り込む」で取り込み、「取り消す」なら何も変えない
  3. 取り込みが終わったら、結果（追加・更新・変更なしの件数）を表示する
- 混ぜる規則
  - 今あるデータにない `id` の記録は、追加する
  - 同じ `id` の記録は、`updatedAt` が新しい方を残す（同じなら変更なし）
  - 今ある記録は削除しない
  - 取り込んだ記録は、`id`、`createdAt`、`updatedAt` を保つ（品名の前後の空白は取り除く）
  - 状態は「予定と食べた」の決まりに合わせて直す。未来の日の「食べた」は「予定」に、過去の日の「予定」は「食べた」にする（`updatedAt` は変えない）。今日の品はファイルの状態のまま
- 取り込みは、全部取り込むか、何も取り込まないかのどちらか。保存に失敗したとき（通信の失敗など）は、データを元のままにしてエラーを表示する

### ブラウザ内の記録をサーバーへ移す

以前の版（記録をブラウザ内の localStorage に保存していた版）の記録は、自動では移りません。次の手順で移します。

1. 以前の版を、記録を入れていたブラウザで開き、データ画面の「書き出す」でファイル（`meal-log-YYYY-MM-DD.json`）を保存する
2. 新しい版（サーバーに保存する版）を開いて会員登録・ログインし、データ画面の「読み込む」で、1. のファイルを選んで取り込む
3. 記録の画面やカレンダーで、記録が移ったことを確かめる。別の端末でも、同じ会員でログインすると同じ記録が見える

書き出したファイルは、別の会員のアカウントでも読み込めます（Cloudflare Access のメールアドレスごとに保存していた版の記録を、会員の記録に移すときも、同じ手順です。`docs/deploy.md`）。

ファイルの形は以前の版と同じなので、そのまま読み込めます。同じファイルを2回読み込んでも、記録は増えません（同じ `id` は「変更なし」になる）。

### 書き出すファイルの形

```json
{
  "version": 1,
  "exportedAt": "2026-11-06T09:30:00.000Z",
  "records": [
    {
      "id": "…",
      "date": "2026-11-06",
      "mealType": "lunch",
      "name": "うどん",
      "genre": "japanese",
      "dishType": "staple",
      "status": "eaten",
      "createdAt": "2026-11-06T03:00:00.000Z",
      "updatedAt": "2026-11-06T03:00:00.000Z"
    }
  ]
}
```

- `version`: ファイルの形のバージョン番号（今は `1`）。形を変えたら上げる（`src/data/dataFile.ts` の `DATA_FILE_VERSION`）
- `exportedAt`: 書き出した日時（ISO 8601、UTC）
- `records`: 記録の一覧。1件の形は下の「記録の形」と同じ（ID、作成日時、更新日時を含む）

## アドレス

選んでいる画面はアドレスのハッシュに入るので、読み込み直しても同じ画面が開き、ブラウザの「戻る」で前の画面に戻れます。

| ハッシュ | 画面 |
| --- | --- |
| なし、`#/` | 今日の記録の画面 |
| `#/day/YYYY-MM-DD` | その日の記録の画面（明日以降の日も）。不正な日付のときは、今日の記録の画面。今日の日付のとき（開いたまま日付をまたいで今日になったときも）は、アドレスを `#/` に置き換えて（履歴は増やさない）今日の記録の画面にする |
| `#/calendar/YYYY-MM-DD` | その日の月のカレンダー（その日を選んだ状態）。実在しない日付のときは、今月のカレンダー（今日を選んだ状態） |
| `#/calendar/YYYY-MM` | その月のカレンダー（今月なら今日を選び、ほかの月は何も選ばない）。不正な月のときは今月（今日を選んだ状態） |
| `#/data` | データ画面（書き出し・読み込み） |
| `#/login` | ログインの画面 |
| `#/login/<結果>` | 確認のメールのリンクを開いた結果を出したログインの画面（API が転送する）。結果は `verified`（確認できた）、`link-used`（使用済み）、`link-expired`（期限切れ）、`link-invalid`（正しくない）、`link-error`（サーバーのエラー）。知らない結果は、ただのログインの画面 |
| `#/login/password-reset` | パスワードを再設定した後のログインの画面（「パスワードを変更しました。ログインしてください」と出す） |
| `#/login/session-expired` | 使っている途中でログインの期限が切れたときのログインの画面（「ログインの期限が切れました。ログインし直してください」と出す）。ログインしていない人が記録の画面などを初めて開いたときは、ただの `#/login` に移る |
| `#/signup` | 会員登録の画面 |
| `#/forgot` | パスワードの再設定のメールを送る画面 |
| `#/reset` | 新しいパスワードを決める画面。再設定のメールのリンク `#/reset/<トークン>` を開くと、トークンを画面の中に持ち、アドレスをこの `#/reset` に置き換える（履歴は増やさない）。トークンがないときは「リンクをもう一度開いてください」 |
| `#/account` | アカウントの画面（ログインしていなければ、ログインの画面） |

カレンダーで月を移ったり、日を選んだりしても履歴は増えません（「戻る」は、カレンダーを開く前の画面に戻ります）。「カレンダー」ボタン、「今日」ボタン、「この日の記録を開く」ボタン、選んでいる日のマスのもう一度のタップ、「データ」ボタン、「アカウント」ボタン、「会員登録へ」ボタン、「ログインへ」ボタン、「パスワードを忘れた」ボタン、「記録の画面へ」ボタン（データ画面のものと、ログイン中に開いたログイン、会員登録、パスワードの再設定、新しいパスワード、アカウントの画面のもの。ログインしていない、またはログインの状態をまだ確かめていないときは、これらの画面には出さない）で画面を移ると履歴が増えます（ログインや会員登録ができて今日の記録の画面に移るときも増えます）。記録の画面から「戻る」と、その日を選んだカレンダーに戻ります。

### 画面を操作するテスト（e2e）の記録

`npm run e2e` は、`npm run dev` の開発サーバー（手元の D1）を使います。テストごとに記録が混ざらないよう、テストごとに別の会員（`e2e-<ランダム>@example.com`）を作って、ログインした状態から始めます（`e2e/fixtures.ts`）。

- 会員の作り方: API で会員登録（`POST /api/auth/sign-up/email`）→ 開発サーバーにためた確認のメール（`/__dev/mails`）のリンクを開いて確認 → API でログイン（`POST /api/auth/sign-in/email`）。そのセッションの cookie を、ブラウザ（`storageState`）と、テストの準備・確かめ用の API の窓口（`MealApi`）の両方に渡す
- テストの準備（記録を入れる）と確かめ（保存された記録を読む）は、同じ会員のセッションで API を直接呼んで行う
- ログインの試す回数の上限（IP アドレスごと）に当たらないよう、テストごと、会員を作るごとに、別の接続元（`CF-Connecting-IP`。試験用の範囲 `198.18.0.0/15` のランダムな値）にする。開発サーバーは、このヘッダーがあればそのまま使う
- 会員登録やログインそのものを試すテスト（`e2e/account.spec.ts`）は、`test.use({ signedIn: false })` で、ログインしていない状態から始める
- テストの会員と記録は手元の D1 に残る。消したいときは `.wrangler/` を消す（手元で `npm run dev` で入れた会員と記録も消える）

## 記録の形

記録は1件が1品です。形は `src/meals/mealRecord.ts` の `MealRecord` にあります。

| 項目 | 内容 | 値 |
| --- | --- | --- |
| `id` | 他の記録と重ならない ID | UUID の文字列（窓口が付ける） |
| `date` | 食べた日／食べる予定の日 | `YYYY-MM-DD`（端末の現地の日付。`toLocalDateString` で作れる） |
| `mealType` | 区分 | `breakfast`（朝）、`lunch`（昼）、`dinner`（夜）、`snack`（間食） |
| `name` | 品名 | 必須。空白だけは不可。前後の空白は取り除いて保存する |
| `genre` | ジャンル | `japanese`（和）、`western`（洋）、`chinese`（中）、`other`（その他）、`null`（未設定） |
| `dishType` | 料理の分類 | `staple`（主食）、`main`（主菜）、`side`（副菜）、`soup`（汁物）、`other`（その他）、`null`（未設定） |
| `status` | 状態 | `planned`（予定）、`eaten`（食べた） |
| `createdAt` / `updatedAt` | 作成・更新の日時 | ISO 8601 の文字列（UTC。窓口が付ける） |

## 保存の窓口

画面からは、保存の窓口 `MealRepository`（`src/meals/mealRepository.ts`）だけを使います。API や localStorage を直接使わないでください。
保存先を差し替えても同じ使い方ができるよう、すべての操作は非同期（`Promise` を返す）です。アプリは、サーバーの API を呼ぶ窓口（下の「サーバーへの保存」）を使います。

| 操作 | 内容 |
| --- | --- |
| `listByDate(date)` | 指定した日の記録を取得する |
| `listByDateRange(from, to)` | `from` から `to` まで（両端の日を含む）の記録を取得する（カレンダー用） |
| `get(id)` | 1件取得する。なければ `null` |
| `create(input)` | 作成する。`genre` と `dishType` は省略すると未設定（`null`） |
| `update(id, changes)` | 渡した項目だけを更新する。`updatedAt` は変わり、`createdAt` は変わらない |
| `delete(id)` | 削除する |
| `markPlannedAsEatenBefore(date)` | `date` より前の日の「予定」（`status` が `planned`）を、すべて「食べた」（`eaten`）にする。更新した記録の `updatedAt` は変わる。更新した記録を返す（なければ空で、保存データは書き込まない）。日が過ぎた予定の自動更新に使う |
| `listAll()` | すべての記録を取得する（書き出し用） |
| `importRecords(records)` | 記録を、`id`・`createdAt`・`updatedAt` を保ったまま一括で保存する（読み込み用）。同じ `id` の記録があれば渡した記録で置き換え、なければ追加する。渡していない記録は変えない。全部保存するか、何も保存しないかのどちらか（1件でも不正、`id` の重複、保存の失敗のときは、保存データは元のまま） |

状態（予定／食べた）と日付の決まり（上の「予定と食べた」）は、画面と自動更新の側で守ります。窓口の `create`、`update`、`importRecords` は、決まりに合わない組み合わせ（未来の日の「食べた」など）も受け付けます。

どの記録を `importRecords` に渡すか（混ぜる規則）は、窓口ではなく `src/data/dataFile.ts` の `planImport` が決めます。

取得した記録は、日付 → 区分（朝・昼・夜・間食の順）→ 作成日時の順に並びます。

- `create` は、作成日時を「今の時刻」と「保存済みのすべての記録の最も遅い作成日時 + 1ミリ秒」の遅い方にする。同じミリ秒に続けて作っても、作った順に並ぶ
- 作成日時まで同じ記録（上の手当てより前に保存されたものなど）は、ID の順に並ぶ（読み込むたびに同じ並びにするため）

エラーになる場合:

- 不正な値（品名が空、日付の書式が違う・実在しない日、区分・ジャンル・料理の分類・状態が決まった値でない、期間の始まりが終わりより後。`importRecords` では、`id` が空、日時の形が違う、`id` の重複も）: `MealValidationError`
- 存在しない ID の更新・削除: `MealNotFoundError`
- 保存データが壊れている、または対応していないバージョン: `MealStorageError`（保存データは上書きしない）
- 保存先が使えない（通信の失敗、サーバーのエラー、ログインの期限切れ）: `MealStorageError`（書き込みに失敗したときは、保存データは元のまま）

### サーバーへの保存

`createApiMealRepository()`（`src/meals/apiMealRepository.ts`）は、サーバーの API（下の「サーバーの API」）を呼ぶ窓口を作ります。アプリは `src/meals/defaultMealRepository.ts` でこの窓口を作って使います。

- 同じオリジンの `/api/` を呼ぶ。ログインの情報（会員のセッションの cookie）は、ブラウザが付ける
- `markPlannedAsEatenBefore(date)` の `date` は、画面が端末の現地の今日の日付を渡す（サーバーの時刻からは決めない）
- API のエラーは、次のように窓口のエラーにする（画面は、ほかの保存先と同じようにエラーを表示する）

| API の応答 | 窓口のエラー |
| --- | --- |
| 届かない（通信の失敗） | `MealStorageError`（「サーバーに接続できませんでした。通信の状態を確かめてください」。`cause` に元のエラー） |
| 401、またはログイン画面への転送（3xx） | `LoginExpiredError`（`MealStorageError` の一種。「ログインの期限が切れました。ログインし直してください」）。画面は、これを受け取ると、ログインの画面（`#/login/session-expired`）に移る |
| 400 | `MealValidationError`（メッセージはサーバーのもの） |
| 404（`type` が `MealNotFoundError`） | `MealNotFoundError`（`get` では `null`） |
| ほかのエラー（500、ない API のアドレスの 404 など）、成功の応答が JSON として読めない | `MealStorageError` |

- 公開の準備までは、サイト全体を Cloudflare Access が守っている。Access は、Access のログインの期限が切れると、ログイン画面（別のオリジン）へ転送する。転送をたどると通信の失敗と見分けられないので、転送はたどらず（`redirect: 'manual'`）、ログインの期限切れとして扱う

### ブラウザ内の保存（画面のテスト用）

`createLocalStorageMealRepository()`（`src/meals/localStorageMealRepository.ts`）は、localStorage に保存する窓口を作ります。アプリでは使いません（ビルドの出力にも入らない）。画面のテスト（`src/**/*.test.tsx`）が、アプリの窓口をこの窓口に差し替えて使います（`src/vitest.setup.ts`）。

- キー `meal-log:meals` に、`{ "version": 1, "records": [...] }` の形の JSON で保存する
- 保存先が使えない（ブラウザの設定などでアクセスが拒否された）、または容量の上限を超えて書き込めない: `MealStorageError`（`cause` に保存先が投げた元のエラーが入る）

## サーバーの API

記録をサーバー（Cloudflare Pages Functions と D1）に保存するための API です。保存の窓口の全操作に対応します。画面は、上の「サーバーへの保存」の窓口を通して使います。

- 入口は `functions/api/[[path]].ts`（`/api/` 以下のすべて）。処理は `server/api.ts`、D1 への保存は `server/d1MealRepository.ts`（窓口 `MealRepository` と同じ操作）
- 検査の規則、並び順、作成日時の決め方は、ブラウザ内の窓口と同じ（`src/meals/mealRecord.ts` と `src/meals/repositoryRules.ts` を共有する）
- 記録は、ログインした会員（会員の ID）ごとに分けて保存する（表 `member_meals`）。すべての読み書き（一覧、期間、1件の取得、更新、削除、一括の取り込み、日が過ぎた予定の更新）をその会員の記録に絞るので、他の会員の記録は、見えず、変えられない（記録の ID を知っていても 404）。別の会員が同じ `id` の記録を取り込んでも、それぞれ別の記録になる
- 処理の順番: マイグレーション → `GET /api/health` → ログインの API（`/api/auth/`）→ 会員の確かめ → 記録の API

### アドレスの表

本文と応答は JSON です。記録1件の形は、上の「記録の形」と同じです。

| 窓口の操作 | メソッドとアドレス | リクエストの本文 | 成功したときの応答 |
| --- | --- | --- | --- |
| `listByDate(date)` | `GET /api/meals?date=YYYY-MM-DD` | なし | 200 `{ "meals": [記録, …] }` |
| `listByDateRange(from, to)` | `GET /api/meals?from=YYYY-MM-DD&to=YYYY-MM-DD` | なし | 200 `{ "meals": [記録, …] }` |
| `listAll()` | `GET /api/meals` | なし | 200 `{ "meals": [記録, …] }` |
| `get(id)` | `GET /api/meal?id=<id>` | なし | 200 `{ "meal": 記録 }`。ないときは 404（`MealNotFoundError`。窓口では `null` にする） |
| `create(input)` | `POST /api/meals` | 作成の値（`date`、`mealType`、`name`、`status`。`genre`、`dishType` は省略すると未設定） | 201 `{ "meal": 記録 }` |
| `update(id, changes)` | `PATCH /api/meal?id=<id>` | 変える項目だけ（例: `{ "status": "eaten" }`。`null` は未設定に戻す） | 200 `{ "meal": 記録 }` |
| `delete(id)` | `DELETE /api/meal?id=<id>` | なし | 204（本文なし） |
| `markPlannedAsEatenBefore(date)` | `POST /api/mark-planned-as-eaten` | `{ "date": "YYYY-MM-DD" }`（基準の日。端末の現地の日付を呼び出し側が渡す。サーバーの時刻からは決めない） | 200 `{ "meals": [更新した記録, …] }` |
| `importRecords(records)` | `POST /api/import` | `{ "records": [記録, …] }` | 204（本文なし） |
| （窓口にはない） | `GET /api/health` | なし | 200 `{ "migrations": ["0001_create_meals.sql", …] }`（当てたマイグレーションの名前。番号順）。ログインなしで開ける |

- `GET /api/health` は、動いていること（D1 につながり、表ができていること）を確かめるためのもの。認証より前に答える。返すのは、`d1_migrations` に記録されたマイグレーションの名前だけ（秘密の値、環境変数、記録、エラーの詳しい内容は返さない）。`GET` 以外は 405（`Allow: GET`）

- 1件の記録は、`id` をクエリで指定する（`<id>` は `encodeURIComponent` でエンコードする）。取り込んだ記録の `id` には `/` や、`.`・`..` だけのものも入りうる。パス（`/api/meals/<id>`）に入れると、`.`・`..` が URL の正規化で消えてしまうため、クエリにしている。`id` がない、空、2つ以上、またはほかの条件があるときは 400
- 一覧は、日付 → 区分（朝・昼・夜・間食）→ 作成日時 → ID の順に並ぶ
- 一覧の取得の条件は、なし・`date`・`from` と `to` のどれか。ほかの組み合わせは 400
- 一括の取り込みは、全部保存するか、何も保存しないかのどちらか（D1 の batch で、1つのトランザクションにする）。記録は100件ずつ JSON の文字列1つにまとめて渡すので、数百件でも D1 の変数の個数の上限に当たらない
- 書き込み（`POST`、`PATCH`、`DELETE`）は、`Content-Type: application/json` のリクエストだけを受け付ける（`DELETE` も付ける。他の Web サイトのフォームからの送信を防ぐため）。ほかは 415
- 書き込みは、cookie で認証するので、`Origin` ヘッダーがあって、リクエストのオリジンと違うときは 403（`Forbidden`）。`Origin` のないリクエスト（`curl` など）は、そのまま受け付ける
- 応答には `Cache-Control: no-store` を付ける

例（`npm run dev` で起動し、画面で会員登録・確認を済ませた会員で。`npm run dev:api` のときは `http://localhost:8788`）:

```sh
curl -c cookies.txt -X POST http://localhost:5173/api/auth/sign-in/email -H 'Content-Type: application/json' -H 'Origin: http://localhost:5173' -d '{"email":"<メールアドレス>","password":"<パスワード>"}'
curl -b cookies.txt 'http://localhost:5173/api/meals?date=2026-11-06'
curl -b cookies.txt -X POST http://localhost:5173/api/meals -H 'Content-Type: application/json' -d '{"date":"2026-11-06","mealType":"lunch","name":"うどん","status":"eaten"}'
```

### ログインの API（`/api/auth/`）

会員の登録とログインは、Better Auth（`better-auth`）で行います。処理は `server/memberAuth.ts`、入口は `server/api.ts`（`functions/api/[[path]].ts` は呼ぶだけ）。画面は `src/auth/` の窓口を通して使います。

| 操作 | メソッドとアドレス | リクエストの本文 | 成功したときの応答 |
| --- | --- | --- | --- |
| 会員登録 | `POST /api/auth/sign-up/email` | `{ "email": "…", "password": "…", "name": "" }` | 200 `{ "token": null, "user": { "email": "…", … } }`。確認のメールを送る。cookie は出さない（ログインした状態にしない）。すでに登録されているメールアドレスでも同じ形の 200 で、そのアドレスに「すでに登録されています」のメールを送る |
| 確認のメールのリンク | `GET /api/auth/verify-email?token=…` | なし | 303 で、ログインの画面（`/#/login/<結果>`）へ転送する。cookie は出さない（リンクを開いた端末ではログインした状態にしない） |
| 確認のメールの送り直し | `POST /api/auth/send-verification-email` | `{ "email": "…" }` | 200 `{ "status": true }`。確認が済んでいない会員のときだけ送る（登録されていない、確認済みのときも同じ応答） |
| 再設定のメールを送る | `POST /api/auth/request-password-reset` | `{ "email": "…" }` | 200 `{ "status": true, "message": "…" }`。登録されている会員（確認が済んでいなくても）にだけ送る。登録されていないメールアドレスでも同じ応答。リンクは `https://<アドレス>/#/reset/<トークン>` |
| 新しいパスワードを決める | `POST /api/auth/reset-password` | `{ "token": "…", "newPassword": "…" }` | 200 `{ "status": true }`。cookie は出さない（ログインした状態にしない）。その会員のすべてのセッションを消す。期限切れ、使用済み、正しくないトークンは 400 `INVALID_TOKEN`、8文字未満は 400 `PASSWORD_TOO_SHORT`（トークンは使えるまま） |
| ログイン | `POST /api/auth/sign-in/email` | `{ "email": "…", "password": "…" }` | 200 `{ "user": { "email": "…", … }, … }`。セッションの cookie を出す。確認が済んでいないときは 403 `EMAIL_NOT_VERIFIED` |
| ログアウト | `POST /api/auth/sign-out` | `{}` | 200。セッションを D1 から消し、cookie を消す |
| ログイン中の会員 | `GET /api/auth/get-session` | なし | 200 `{ "user": …, "session": … }`。ログインしていなければ `null` |

- マイグレーションと `/api/health` の後、会員の確かめより前に処理する（ログインしていなくても使う）
- `BETTER_AUTH_SECRET` がないときは 500（`AuthConfigurationError`）。記録の API も、会員を確かめられないので同じく 500 になる
- 記録の API（`/api/meals` など）は、ここで出したセッションの cookie で使う（下の「認証」）
- パスワードは8文字以上。メールアドレスは小文字にそろえる。メールアドレスの確認が済むまで、ログインできない（上の「登録とログインの流れ」）
- 確認のメールのリンクは、API のアドレス（`/api/auth/verify-email?token=…`）。画面のアドレスはハッシュ（`#/…`）なので、トークンはクエリにして API で受け取り、確認の結果をハッシュのアドレス（`/#/login/<結果>`）にして転送する。トークンは、Better Auth が秘密の値 `BETTER_AUTH_SECRET` で署名したもの（有効期限は24時間）。使用済みかどうかは、確かめる前に、その会員が確認済みだったかで見分ける
- 基準のアドレス（オリジン）は、リクエストのアドレスから決める（プレビューは公開ごとにアドレスが変わるため）。ほかのオリジンからのリクエスト（`Origin` がない cookie 付きのリクエストも）は 403
- セッションの cookie には `HttpOnly`、`SameSite=Lax` を付け、`https` のときは `Secure` も付ける（手元の `http` では付けない）
- 試す回数の上限（総当たりを防ぐ）: IP アドレス（`CF-Connecting-IP`）ごとに、登録、ログイン、確認のメールの送り直し、再設定のメールを送る、新しいパスワードを決めるは10分に10回、ログアウトは10分に30回、ほかは1分に100回まで（`server/memberAuth.ts` の `AUTH_RATE_LIMITS`）。超えると 429 `{ "code": "TOO_MANY_REQUESTS", "message": "試す回数の上限を超えました。…" }`（`Retry-After` に待つ秒数）。数えた値は D1 の表 `rateLimit` に保存する
- メールを送る回数の上限: 会員登録、確認のメールの送り直し、再設定のメールを送るは、同じ宛先のメールアドレスと同じ IP アドレスの組み合わせごとに、10分に3回まで（`server/mail/mailRateLimit.ts` の `MAIL_RATE_LIMIT`）。登録の有無を探られないよう、実際に送るかどうかに関係なく数える。超えると 429 `{ "code": "TOO_MANY_MAIL_REQUESTS", "message": "メールを送る回数の上限を超えました。…" }`。数えた値は同じ表 `rateLimit` に、`key` を `mail:` で始めて保存する（宛先のメールアドレスは SHA-256 のハッシュにして入れる）
- エラーの応答は Better Auth の形（`{ "code": "…", "message": "…" }`）。例: パスワードが違う・存在しないメールアドレスは 401 `INVALID_EMAIL_OR_PASSWORD`、確認が済んでいないは 403 `EMAIL_NOT_VERIFIED`、パスワードが短い・メールアドレスの形が違うは 400、再設定のリンクが使えないは 400 `INVALID_TOKEN`（期限切れ・使用済み・正しくないを区別しない）。画面は `code` から日本語の説明を出す（`src/auth/apiAuthClient.ts`）
- メールを送れなかったときは、API のエラーの形（下の「エラー」）の 500 にする: メールの環境変数が足りないときは `MailConfigurationError`、Resend が失敗を返したときは `MailSendError`。どちらも、秘密の値と宛先のメールアドレスは、応答と記録に出さない。ただし再設定のメールは、登録されている会員にだけ送るため、500 にすると登録の有無が分かってしまう。そのため、送れなくても 200 の同じ応答にして、記録にだけ残す
- パスワードの再設定は Better Auth の `request-password-reset` と `reset-password` を使う。トークン（Better Auth が作ったもの）は、リンクではハッシュの中（`/#/reset/<トークン>`）に入れ、新しいパスワードを送るときは本文に入れる（アドレスのクエリに入れると、サーバーの記録に残るため）。有効期限は1時間（`RESET_PASSWORD_EXPIRES_IN`）、再設定したら全セッションを切る（`revokeSessionsOnPasswordReset`）

### メールの部品（`server/mail/`）

メールは Resend（<https://resend.com>）の API（`https://api.resend.com/emails`）を `fetch` で呼んで送ります（SDK は使わない）。Better Auth からは、この部品を通してだけ送ります。

- `server/mail/mailer.ts`: メールを送る部品（`createMailer`）。送る部分（`MailTransport`）は差し替えられる。本番とプレビューは Resend（`createResendTransport`）、テストと手元の開発サーバーは偽物（メモリーにためる）
- 送信元は `meal-log <MAIL_FROM の値>`（表示名は meal-log）
- `MAIL_ALLOWED_TO` があって、宛先が違うときは、送らず、エラーにもしない（画面は送ったときと同じ）。記録には「送り先が許可されていないので送らなかった」とだけ残し、宛先は出さない
- `server/mail/mailRateLimit.ts`: メールを送る回数の上限

#### メールの文面

文面は `server/mail/templates/` にあります。文字だけの版（`text`）と、簡単な HTML の版（`html`）を、1つのファイルに書きます（共通の HTML の枠は `layout.ts`）。直すときは、このファイルを直します。

| ファイル | 送るとき | 件名 |
| --- | --- | --- |
| `verifyEmail.ts` | 会員登録したとき、確認のメールを送り直したとき | 【meal-log】メールアドレスの確認 |
| `alreadyRegistered.ts` | すでに登録されているメールアドレスで、会員登録しようとしたとき | 【meal-log】このメールアドレスはすでに登録されています |
| `resetPassword.ts` | 「パスワードを忘れた」から、再設定のメールを送ったとき（登録されている会員にだけ） | 【meal-log】パスワードの再設定 |

- どのメールにも「このメールに心当たりがなければ、無視してください」と書く
- HTML の版に入れる値（リンクなど）は `escapeHtml` を通す
- 応答には `Cache-Control: no-store` を付ける
- Better Auth は Node.js の `AsyncLocalStorage` を使うので、Pages の互換性フラグ `nodejs_compat` が要る（手元は `wrangler.dev.jsonc` と `npm run dev:api`。本番とプレビューは `docs/deploy.md`）

### エラー

エラーの応答の本文は `{ "error": { "type": "…", "message": "…" } }` の形です。`type` でエラーの種類を見分けます（`message` は日本語の説明）。

| 状態コード | `type` | 場合 |
| --- | --- | --- |
| 400 | `MealValidationError` | 不正な値（窓口の `MealValidationError` と同じ規則）。本文が JSON のオブジェクトとして読めないときも |
| 401 | `Unauthorized` | 記録の API で、ログインしていない（セッションの cookie がない）、セッションが無効か期限切れ（ログアウトした後も）、メールアドレスの確認が済んでいない |
| 403 | `Forbidden` | 記録の API の書き込みで、`Origin` がリクエストのオリジンと違う |
| 404 | `MealNotFoundError` | 存在しない ID の取得・更新・削除（他の会員の記録の ID も） |
| 404 | `RouteNotFound` | ない API のアドレス |
| 405 | `MethodNotAllowed` | アドレスが対応していないメソッド（`Allow` ヘッダーに使えるメソッド） |
| 415 | `UnsupportedMediaType` | 書き込みの `Content-Type` が `application/json` でない |
| 500 | `MealStorageError` | 保存先（D1）の失敗、保存データが壊れている |
| 500 | `AuthConfigurationError` | 認証の環境変数 `BETTER_AUTH_SECRET` が足りない（ログインの API と記録の API） |
| 500 | `DatabaseNotConfigured` | D1 がつながっていない（Pages の設定で、D1 を `DB` の名前でつないでいない） |
| 500 | `MigrationError` | 表の変更（マイグレーション）を当てられなかった（詳しい内容は応答に出さず、サーバーのログに残す） |
| 500 | `MailConfigurationError` | メールの環境変数（`RESEND_API_KEY`、`MAIL_FROM`）が足りないので、メールを送れない（会員登録、確認のメールの送り直し。再設定のメールは、登録の有無を探られないよう 200 のまま、記録にだけ残す） |
| 500 | `MailSendError` | Resend がメールの送信に失敗を返した、または Resend に接続できない（`message` には Resend の状態コードだけを入れる） |

`DatabaseNotConfigured` と `MigrationError` は、認証より前に確かめるので、ログインしていなくても返ります。

### 認証

記録の API は、会員のログイン（上の「ログインの API」）のセッションの cookie で、本人を確かめます（`server/memberAuth.ts` の `getMember`。Better Auth の `getSession` を使う）。

- セッションは、リクエストごとに D1 で確かめる。ログアウトした、パスワードを再設定した、期限が切れたセッションは使えない
- メールアドレスの確認が済んでいない会員のセッションは、ログインしていないのと同じに扱う（401）
- 会員の ID（表 `user` の `id`）で、記録を絞る
- 公開の準備までは、Cloudflare Access がホスト全体を守っている（`docs/deploy.md`）が、API は Access のログインの情報を見ない（本人の確かめには、会員のセッションだけを使う）

### 環境変数

| 名前 | 内容 | 本番 |
| --- | --- | --- |
| `DB` | D1 のデータベース（バインディング） | 設定する（Cloudflare 側で） |
| `BETTER_AUTH_SECRET` | 会員のログイン（Better Auth）が、セッションなどの署名に使う秘密の値（推測されにくい長いランダムな文字列） | **必須**（秘密の値として。本番とプレビューで別の値） |
| `RESEND_API_KEY` | メールを送る Resend の API キー（`re_…`）。秘密の値 | **必須**（本番用のキー。プレビューとは別） |
| `MAIL_FROM` | メールの送信元のアドレス（例: `onboarding@resend.dev`）。表示名は meal-log になる | **必須**（ドメインを取るまでは `onboarding@resend.dev`。取った後は、そのドメインのアドレス） |
| `MAIL_ALLOWED_TO` | 任意（プレビュー用）。設定すると、このアドレスにしかメールを送らない（カンマで区切って複数書ける）。ほかの宛先は、送らずに記録だけ残す | **本番に設定しない**（設定すると、所有者以外にメールが届かなくなる） |

- 本番の値（D1 のデータベース ID、`BETTER_AUTH_SECRET`、`RESEND_API_KEY`、`MAIL_FROM`）は、リポジトリに書かず、Cloudflare 側で設定する（`docs/deploy.md`）
- `BETTER_AUTH_SECRET` がないときは、ログインの API（`/api/auth/` 以下）と記録の API（`/api/meals` など）が 500（`AuthConfigurationError`）になる。`/api/health` は、なくても動く
- 手元では、`npm run dev`（`server/devApi.ts` の `DEV_BETTER_AUTH_SECRET`）と `npm run dev:api`（コマンドの `--binding`）が、起動するときだけ開発専用の値を設定する。リポジトリの設定ファイル（`wrangler.dev.jsonc` など）には書かない
- `RESEND_API_KEY` か `MAIL_FROM` がないときは、メールを送るとき（会員登録、確認のメールの送り直し）だけ 500（`MailConfigurationError`）になる。会員登録ができないので、本番では必須
- 手元の `npm run dev` は、メールを送らずにためるので、`RESEND_API_KEY` は要らない（`MAIL_FROM` は `server/devApi.ts` の `DEV_MAIL_FROM` を起動するときだけ設定する）

### D1 の表

表のスキーマは、`migrations/` の下のマイグレーションのファイルで管理します。

- 表 `member_meals`: 記録。1行が1品（`migrations/0003_create_member_meals.sql`）。列は記録の項目（`meal_type` のように小文字とアンダースコアの名前）と、会員の ID の列 `user_id`（表 `user` の `id` への外部キー。会員が消えると、その会員の記録も消える `ON DELETE CASCADE`）
  - 主キーは `user_id` + `id`。日ごと・期間の取得用に、`user_id` + `date` の索引がある
- 表 `meals`: 古い記録の表（Cloudflare Access のメールアドレスの列 `user_email` ごとの記録）。API は使わない。所有者が、書き出しと読み込みで記録を会員の記録へ移したことを確かめた後に、別の Issue で消す

- 表 `user`、`session`、`account`、`verification`、`rateLimit`: 会員のログイン（Better Auth）が使う表（`migrations/0002_create_auth_tables.sql`）。形は、使っている版の Better Auth が期待するものに合わせている。パスワードは、ハッシュにして `account` に入る

#### マイグレーションは、アプリが自分で当てる

本番・プレビュー・手元のどれでも、API が、自分のつながっている D1 に、まだ当てていないマイグレーションを当てます（`server/migrate.ts`）。手で当てる必要はありません。

- `migrations/*.sql` は、ビルドやテストの前に `npm run bundle-migrations`（`scripts/bundle-migrations.mjs`）が `server/migrations.generated.ts` に書き出し、アプリに含める。書き出したファイルはコミットしない（`.gitignore`）
- API の入口で、その実行環境で最初のリクエストのときに1回だけ確かめ、まだのものを番号（ファイル名）の順に当てる。認証より前に行うので、ログインしていないリクエストでも当たる。2回目からは確かめない。失敗したときは 500（`MigrationError`）を返し、次のリクエストでやり直す
- 当てたものは、wrangler と同じ表 `d1_migrations`（`id`、`name`、`applied_at`）に記録する。`wrangler d1 migrations apply`（`npm run db:migrate:local` や、`docs/deploy.md` の緊急用の手順）で当てた D1 とも食い違わず、どちらも適用済みのものは飛ばす
- 1つのマイグレーションの SQL と記録は、D1 の batch（1つのトランザクション）で書く。途中で失敗したら、SQL も記録も残らない。同時に別のリクエストが同じものを当てていたら、記録の名前の重なりで取り消されるので、記録を読み直して次に進む（二重に当てない）
- 文は `;` で区切る（`--` で始まる行はコメントとして除く）。文字列の中に `;` を書かない

#### 表の変更の決まり（足すだけ）

公開（新しいプログラム）とマイグレーションは同時ではないので、少しの間、新しいプログラムと古い表、または古いプログラムと新しい表が並びます。どちらの組み合わせでも動くよう、表の変更は「足すだけ」を基本にします。

- 変えるときは、新しい番号のファイルを `migrations/` に足す。一度入れたファイルは変えない
- 表や列を足す。足す列は、空（`NULL`）を許すか、既定の値（`DEFAULT`）を持たせる
- 列や表を消す・名前を変えるのは、プログラムがそれを使わなくなってから、別の Issue で行う
